No queue record, claim, lease, token, reservation or broker format change versus the live generation 04f6f00e0410. Two claim-side changes on that base. (1) The #1526 carry: the claim-time admission decision in pool.py holds back a portable CPU row on a host that has a ready GPU row, with documented exceptions; it adds one denial reason string, deferred_for_ready_gpu, and one evidence field, drain_resolves, on denial diagnostics. (2) Container-image eligibility: a bare sha256: container_images requirement is now also satisfied by the digest part of any RepoDigest in a box's image inventory (one shared predicate, container_images.satisfied, used by the offer-side placement match, the early admission check and the claim-time check), so one image that the containerd store names by its index digest and the classic store names by its config digest, carrying that index digest only as a RepoDigest, places on both Sparks. A repository@sha256: requirement and a content: requirement stay exact. Sealing, action keys, the inventory record schema, its TTL and the claim freshness are unchanged, so rows already sealed (for example fd9ca6b5) start matching with no resubmission. Mixed-generation interval: an old-generation loop still applies exact membership, so until every loop has restarted onto this generation an old loop on the classic-store box can still deny such a row with container_image_absent before any reservation is taken (no attempt is spent), and a new-generation loop may defer a CPU row for up to 20 s toward a box whose old loop then refuses it; no host is fenced for a gang that cannot form. Loops restart onto the new generation as they become idle; a running action finishes under the generation that claimed it. Not in this generation: the #1533 withdrawn-claim carry and any RAM tier policy change.
