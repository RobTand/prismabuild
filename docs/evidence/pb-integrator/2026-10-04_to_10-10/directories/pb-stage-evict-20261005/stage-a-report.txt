Proposed removal and accounting design

Extend the existing stage_release reconcile path with an explicit bounded source-mark-only operator pass, and tests. A thin operator entry point using the same ownership census and locks is preferable to a separate deletion implementation. The current reconcile categorically leaves source-mark-only files, so it cannot remove these files unchanged. Its source-mark classification, stage containment, ownership locking, fresh census and identity-since-walk structure are appropriate reuse points. The history-bound recover_orphaned_range is not needed for unused-file proof; do not add head/egress receipt or sealing prerequisites for this operation.

For the current CONFIRMED_GARBAGE set only: take the stage ownership lock in bounded batches; immediately before each unlink, recheck the source's recorded size/time/inode and extent, the stage file's captured identity and marks, fragment ownership, current pins, claimed destinations, promotion sources, live plans and queued rows, local handles, and server-side open state. Abort the whole run on the first unexpected holder, changed source or file, unreadable census, or unlink error. Log each successful deletion's full path, size and time. Only after confirmed deletion may any associated token settlement occur, with the tier mint lock taken as the leaf in the existing lock order.

For this particular 5,423-file set, the associated token release is zero: no key holds those bytes. Deleting them grows actual writable space; the ordinary guarded stage supply mint can recognize that space afterwards. Do not release rounded receipt slack, borrow tokens from another mover, or release the receipt-less funding key to compensate for deleting uncharged files.

The 44,871 retained files should not be included in that simple pass. Existing fragment owners must be retired through the ordinary owner-aware machinery so their published vouches and material do not survive deleted data. Similarly, true shared-copy duplicate charges should use stage_release's existing shared-decharge settlement at lines 3115-3175: remove a retiring owner's vouch and destroy redundant occupancy tokens while the surviving owner still accounts for the unchanged file; do not return occupied capacity to the free ledger. Last-owner deletion precedes release of its final charge. This is separate from deleting the confirmed-garbage list and from repairing the two-token precommit hold.

The prose assertion that held tokens literally equal bytes on stage is not the implemented arithmetic: tokens round each range upward and may include funding in flight and overlapping ownership. The comparison should distinguish physical unique payload, ownership-weighted receipt payload, rounded reservations, and unsettled funding. Report and test those quantities separately rather than treating raw equality with an unrounded receipt total as an invariant.

Before any live operation, the lead's Stage B assignment requires private-queue and fixture-stage tests through PrismaBuild, pbtest.py with the x86 tag, with collected equal to ran. Test source-only reclaim, source absence/change, a newly published holder or reader lease, stage replacement, open-handle retention, abort-on-anomaly behavior, and delete-before-settlement ordering. No such implementation or test run was attempted in Stage A.
