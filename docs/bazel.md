# Bazel

Bazel runs the merge gate's test population on BuildBuddy, one target per test
file. That population is the set of files the hosted `gate` runs. The hosted
gate's own files stay the sources of truth:

- `tools/ci/gate_select.py` and `tools/ci/gate_paths.py` supply the dependency
  evidence.
- `tools/ci/gate_quarantine.json`, `tools/verify.py` and
  `tests/proof_execution.json` decide which files run.
- `tools/ci/gate_budget.json` sets per-test budgets.
- `tools/ci/gate_requirements.txt` pins the packages.

A contended executor can push a passing test over its budget. Every overrun
is a warning. When all collected tests pass, `tools/bazel/python_runner.py`
keeps exit status zero and writes `budget-warnings.json` beside the inventory
in its test outputs. Each row names the test node, measured `seconds` and
configured `budget_seconds`. The gate collects plain, zipped and sharded
outputs into `budget_warnings`, adding the target `label` and, after a merge,
the `architecture`. The result and GitHub summary show those warnings without
changing the verdict. The hosted lane reports the same warning policy.

The gate never reruns a target for a budget overrun or `TIMEOUT`. A hard Bazel
`TIMEOUT`, assertion failure or missing result remains a failure. The static
`budget_check` still rejects growing budgets; the limits remain the yardstick
for warnings.

## Running tests

Run Bazel on BuildBuddy, never with a local Bazel server on a fleet host.
`bb remote` runs the Bazel client on a BuildBuddy runner, mirrors your
uncommitted changes, and sends every test to remote execution:

```sh
BUILDBUDDY_API_KEY="$(cat ~/.config/buildbuddy/api_key)" GIT_REPO_DEFAULT_BRANCH=main \
  bb remote \
  --container_image=docker://gcr.io/flame-public/rbe-ubuntu24-04@sha256:5f0c01e5f6d79e58d7a996330de33aa38ce599bf8431eaf27521e7602daadf50 \
  --runner_exec_properties=EstimatedCPU=4 --runner_exec_properties=EstimatedMemory=8GB \
  --runner_exec_properties=EstimatedFreeDiskBytes=50GB \
  test //... --config=remote
```

To run less, replace `//...` with one test file's target, such as
`//tests:test_core`. Read the verdict from the command's exit status and the
invocation it links, not from the start message.

Each remote test runs a private copy of the Python interpreter, on amd64 and
arm64. Executors hardlink inputs from a shared cache; other actions linking or
unlinking the shared interpreter change its ctime while PrismaBuild hashes it,
even when its contents stay the same. A private interpreter keeps this metadata
independent. `test_proof_runtime_observation`, which requires a root-owned
interpreter, runs in the hosted lane because the private copy belongs to the
remote test user.

Use local Bazel only for short generation and query commands. Pass
`--max_idle_secs=300` (for example `bazel --max_idle_secs=300 query ...`) so
the server doesn't stay on a fleet host.

## How the build is generated

Every `BUILD.bazel` except `tools/bazel/BUILD.bazel` is generated by
`tools/bazel/build_files.py`. Gazelle can't express PrismaBuild's imports:
- test modules import other test modules, and a `py_test` can't be a
  dependency;
- modules import each other in cycles;
- conftest puts directories on `sys.path` at run time;
- modules load other modules by path.

The gate selector already reads all of these, so the generator turns the same
evidence into targets:

- **One library per module**, and one per import cycle. Library edges come
  from import statements anywhere in a file (inside functions too), imports
  in embedded `python -c` snippets, literal `import_module` and `__import__`
  names, `pytest_plugins`, exact loader paths, and, in tests, exact paths to
  `src/` and `tools/` modules. A bare string is not an import.
- **Data for files a module names by path,** read from the repository root. A
  path to a test file, or a glob, is data, not an edge. A whole directory
  becomes one `files/<directory>` filegroup. A bare directory name doesn't
  count, as in the selector. In production code only exact files and
  `with_name` siblings are data; tree reads from publishing and bundling
  are not.
- **A test target's own inputs,** which never reach other tests:
  - modules the test file names in strings, when it imports by name;
  - the tree reads of production modules it imports directly;
  - the programs its code launches, file by file. A `.py` path counts only
    where it reaches `subprocess`, `os.exec*`, `runpy` or a loader, or is a
    bare file name that a path is built from. When a launch's arguments can't
    be followed, every exact path in that module counts
    (`tools/bazel/build_files.py --uncertain` lists them). A name in a process
    table or a log line is not an input.
  - `tools/bazel/test_inputs.bzl`, for reads through a root a caller passes,
    each with its reason.

  A test that reads an undeclared repository file finds it missing on the
  remote executor and fails; it doesn't pass silently.
- **One `pb_py_test` per test file.** It runs `tools/bazel/python_runner.py`,
  which runs pytest on that file from the repository root, the way
  `tools/ci/gate_run.py` runs a hosted shard. It uses both conftest files,
  `pyproject.toml`, the gate's environment, its node-level deselects and its
  per-test budgets.
- **Population tags.** A test file outside the hosted gate's population still
  has a target, tagged `manual` plus `gate-lane-<lane>` or `gate-issue-<n>`.
  `//...` skips it.
- **Shards.** A file that takes more than 40 s on hosted runners is split into
  Bazel test shards.

Packages are `//`, `//src/prismabuild`, `//tools`, `//tests` and the
hand-written `//tools/bazel`. `tools` is one package because an import cycle
joins `tools/fleet` and `tools/maintenance`.

## Adding a test file

1. Add `tests/test_<name>.py`.
2. Run `tools/bazel/generate.sh`.
3. Commit the `BUILD.bazel` changes it writes.

The same applies after you add a module, add an import, or add a fixture that
a test names by path. No hand edits are needed.

- **A test that can't be hermetic** goes in `tools/bazel/nonhermetic.bzl` with
  its reason. Remote test actions have no network and run as an unprivileged
  user unless listed there.
- **New pins** go in `tools/ci/gate_requirements.txt`. Then run
  `tools/bazel/generate.sh`, which also writes `tools/bazel/requirements.txt`.

## Where tests run

Most tests run on BuildBuddy's remote executors. An executor is a container
that differs from a hosted runner in ways some tests notice:
- it has a few CPUs of a larger host;
- it has no network, no sudo, no `.git` and a 64 MB `/dev/shm`;
- remote execution stages every input as executable;
- `/tmp` is overlay, which PrismaBuild's state directories refuse.
- inputs are hardlinks into a shared file cache. On arm64 the interpreter's
  ctime moves while other actions link it, so there each test runs a private
  copy of the interpreter, owned by the test user.

The runner gives every test a short `TMPDIR` on the execroot's local
filesystem. It also removes Bazel's own variables from the environment pytest
sees.

`tools/bazel/nonhermetic.bzl` names the tests that need more, each with its
reason:

- **`runner`:** the test runs on the Remote Bazel runner itself. The runner is
  a VM like a hosted runner, with all its CPUs, sudo and network. pytest runs
  in the runner's git checkout. Before the test, the runner prepares the VM
  as `tools/ci/gate_setup.py` prepares a hosted shard: `/home/rob/pbt17`, the
  packages the hosted image has, and a cgroup of the test's own. Its result is
  never cached, and it may not leave a process running.
- **`hosted`:** Bazel never runs the test; the target is `manual`. The Gate
  workflow's hosted lane runs it with `tools/ci/gate_run.py` on a GitHub-hosted
  runner, exactly as the old gate did, whenever Bazel's selection impacts it.
  Parity counts it as run.
- **`hosted-arm64`:** BuildBuddy's arm64 executors can't host the test. Most
  of these need a disk: most arm64 executor hosts keep every writable path on
  an unsized tmpfs, which PrismaBuild's disk checks refuse and `statvfs` reports as 0
  bytes free, and Firecracker isolation, which would give a disk, fails to
  start there. The executors' speed also varies enough to push a test past its
  time budget. The test runs on amd64 executors as usual. After a merge, the hosted lane runs it on
  `ubuntu-24.04-arm` instead of the arm64 executors.
- **`requires-network`:** the remote executor gets a network.

CI fails when a generated input is stale (`tools/ci/bazel_generated.py`). It
also fails when Bazel's tests differ from the hosted gate's population
(`tools/ci/bazel_parity.py static`). Both name the file and the fix:
`tools/bazel/generate.sh`.

## Configurations

- `--config=remote`: BuildBuddy cache, remote execution on the pinned Ubuntu
  24.04 image in `selfhosted-amd64` on dl380g10, build events, `--jobs=40`.
- `--config=remote-arm64`: the same, but every action runs on BuildBuddy's
  `selfhosted-arm64` executors on the Sparks. The amd64 client drives both
  action architectures.
- `--config=ci`: CI build metadata, a refusal of a stale `MODULE.bazel.lock`,
  and the per-test receipts parity reads.

Both execution platforms require self-hosted executors. Unavailable pool
capacity fails or waits within the existing timeout; actions never fall back
to cloud or local execution. The Remote Bazel runner keeps its existing cloud
Firecracker request, normally 4 CPUs and 8 GB, plus its current disk reservation.
Runner-lane tests, GitHub-hosted lanes and ARM exclusions keep their current
placement. Moving the runner itself requires separate compatibility work.

Pass the API key header from the environment or a private rc file. Never commit
it.

## Measured test sizes

`tools/bazel/test_sizing.bzl` lists remote test actions whose measured CPU
bursts exceed the default one CPU. `pb_py_test` adds each entry's execution
properties to the properties from `nonhermetic()`. Tests without an entry
keep their existing properties, tags, and environment.

Use all three properties when reserving a measured size on BuildBuddy Cloud:

```python
exec_properties = {
    "EstimatedComputeUnits": "1",
    "EstimatedCPU": "2",
    "EstimatedMemory": "0.5GB",
}
```

A nonzero `EstimatedComputeUnits` disables both measured and predicted task
sizing. The explicit CPU and memory values override its coupled defaults of
one CPU and 2.5 GB per compute unit. Always specify memory too, to avoid
reserving that default for a small test.

`EstimatedCPU` alone does not force the scheduler to use that size. In the
2026-11-02 calibration, an action requested 4000m CPU and 2 GB, but the
scheduler chose a prediction of 1000m and 448,631,104 bytes. With the three
properties above, the second calibration's receipts showed the requested
4000m and 2,147,483,648 bytes as the effective size, with no prediction or
measurement replacing them.

Read the execution receipt, rather than inferring allocation from the action's
platform. Request `rpc/BuildBuddyService/GetExecution` with
`{"executionLookup":{"invocationId":"<test invocation>"},"inlineExecuteResponse":true}`.
For each test action, inspect
`executeResponse.result.executionMetadata.auxiliaryMetadata` for the
`execution_stats.ExecutionAuxiliaryMetadata` record. Its
`schedulingMetadata.requestedTaskSize` is the request;
`schedulingMetadata.taskSize` is the effective allocation. CPU is in
`estimatedMilliCpu`, memory in `estimatedMemoryBytes`. The same record gives
the execution priority and `cgroupSettings`.

Cloud's default isolation is OCI. In both calibrations its cgroups had
`cpu.max = 3000000 100000`, a global 30-core quota, and
`memory.max = max`. The requested size controls scheduling, CPU weight, and
the leased cpuset; it is not a per-request CPU hard cap. Firecracker treats
sizes as hard limits and needs a separate calibration. Do not assume every
cloud executor configuration matches the sampled OCI containers.

To repeat calibration, select the problem targets and tests which launch
children, including users of process-backed broker fixtures. Exclude hosted
targets. Runner-lane tests share the runner VM's cgroup, so their samples do
not justify remote-executor reservations. Use the Remote Bazel command above
with `--jobs=16`, `--nocache_test_results`,
`--run_under=//tools/bazel:calibrate_tests`, and temporary overrides:

```sh
--remote_exec_header=x-buildbuddy-platform.EstimatedComputeUnits=1 \
--remote_exec_header=x-buildbuddy-platform.EstimatedCPU=4 \
--remote_exec_header=x-buildbuddy-platform.EstimatedMemory=2GB
```

Verify the effective size in the receipts before using the measurements.
The wrapper samples cgroup CPU usage every 100 ms, including children which
exit between samples. It records the maximum CPU burst, peak memory, and
sampled live process count in `test.outputs/sizing.json` and the test log.
Process counts exclude the sampler and include the test launcher and pytest;
they are lower bounds because short-lived children can escape sampling.

Save those records as a JSON object mapping target labels to lists of
samples, and save the `GetExecution` response. Derive the requests with:

```sh
python3 tools/bazel/sizing_report.py \
  --executions executions.json --samples samples.json > measurements.json
```

The derivation rounds bursts above 1.25 CPUs up to whole CPUs. It leaves
smaller bursts at the default, allowing for the sampler's overhead. Memory
gets 25 percent headroom, rounded up to 0.25 GB with a 0.5 GB minimum, only
for targets receiving CPU overrides. Each table entry records its burst,
sampled process count, and source-based reason. Calibration wall times are
observations, never test assertions.

The [2026-11-02 measurements](../tools/bazel/test_sizing_measurements.json)
cover 220 isolated remote targets from a 236-target calibration. Sixteen
runner-lane targets were observed but excluded from per-action sizing.
The table reserves two CPUs for 65 targets, three for seven, and four for
one. The other 147 measured targets keep dynamic sizing. Memory requests
are 0.5 GB except `test_allowance_suite_filesystem_isolation`, which needs
0.75 GB after headroom. The source evidence has 15 assertion-failing targets
and eight timeouts, or 23 distinct targets, despite the original README's
count of 24; calibration includes all 90 baseline failures and timeouts.

## CI

The Merge gate workflow (`.github/workflows/gate.yml`) starts
`tools/ci/bazel_gate.py` on a Remote Bazel runner through
`tools/ci/remote_gate.py`. It reads back `gate-result.json`, which the runner
leaves as a BuildBuddy artifact.

- **Ordinary pull requests** test GitHub's merge commit against its first
  parent, current `main` (#2540). Their check is `pr-gate`.
- **Mergify's batch drafts** test their exact head against the queue-aware base
  that `gha-mergify-ci`'s `scopes-git-refs` returns. Their check is `gate`.
- **Both checks** require the Bazel verdict, a scope list that reached Mergify,
  and the hosted lane whenever selection impacted one of its targets.

Selection fails closed. The gate fails when:
- the base or head is missing;
- bazel-diff fails;
- a changed file is read by no target and isn't in `IRRELEVANT`;
- build-relevant changes impact no target;
- the remote result is missing or malformed;
- Mergify doesn't receive the scope list.

Some changes test everything and mark the pull request as touching every
scope:
- changes matching `FALLBACK`: Bazel files, `tools/bazel/`, the requirements,
  workflows, and the selector's evidence code;
- a `BUILD.bazel` edit that moves no rule.

Impacted targets that no test depends on are built.

Each push to `main` runs every test on amd64, then on arm64 remote executors,
and the hosted lane on both architectures. The arm64 pass leaves out the
`runner` tests (Remote Bazel runners are amd64 only) and the `hosted-arm64`
tests; `gate-result.json` counts them under `architectures.arm64.excluded`, and
the arm64 hosted lane runs their files. An architecture whose Bazel invocation
runs no test at all is an error naming the invocation and its first `ERROR`
line, not a failure of every test. A failure names the merged pull
requests and says whether their selection included the failing test. The job
summary and the `post-merge-<sha>` artifact hold one `POST_MERGE_RECORD`
JSON line per run.

## Graph impact

Every PR and main gate compares both revisions' Bazel graphs, including when
selection falls back to all tests. `graph_impact` in `gate-result.json` records
U, LOC-weighted U, every test's source reach count, reach percentiles, SCC members,
added edges and failures. The log always prints one summary line.

The original v42 source-edge probe found no source files in `--depEdgesFile`.
The adapter supplements the dependency file with one batched `kind("source file", deps(tests(//...)))` query per revision with
`--output=streamed_jsonproto`, plus one rule-metadata query to attach those
files to their consuming rules. Reach counts repository source-file labels,
including declared data. External repository labels are excluded. The test
population is `tests(//...)` minus `manual`. Cycles already collapsed into a
Bazel library remain one graph node; Bazel rejects rule dependency cycles.

`tools/ci/graph_impact.py` is vendored byte-identically from PrismaQuant commit
`75aff74ae1351a279eff79dd45947623d956faa4`. A test pins SHA-256
`44b136779589d8ce26d3f321f714120e071405e77b913fc76e6fc2cefc751e19`.
Its `measure` and `compare` functions accept graph facts. PrismaBuild keeps
the default strict test-to-test policy without an override. The gate supplies
each test's Bazel package, the base maximum reach per package, and added and
removed `rule_to_rule` and `rule_to_source` edges classified by Bazel kinds.
`import_fanout.py` remains a thin compatibility wrapper. The gate and wrapper use the
pure `bazel_imports.py` adapter on the same library edges. This keeps the
checks independent of gate configuration inputs and the old scanner path. Data references and
test wrappers are not library imports.

New or changed tests may inherit their package's base maximum reach. New
packages use the global p90 budget; edited tests may keep their own base
reach. A structural regression adds edges that increase existing-source
fanout or existing-test reach. New tests and sources that inherit their
package's reach are reported without failing. U and LOC-weighted U are trend
figures: explicit baseline writes keep their minima, and their rise never
fails a PR. SCC maximum and edge rules still fail. Every growing, merged or
entirely new cycle fails even when an unrelated larger cycle masks the maximum.

Every failure includes native `bazel-diff explain --format mermaid` output.
Generation, selection and explanations use the same URL- and SHA-256-pinned
bazel-diff v70.0.2 native binary. Historical proofs compare its complete impacted
Rule sets with v42 on two ranges. The gate runs on amd64 Remote Bazel runners,
including for arm64 test actions.

The existing `tests/fixtures/import_fanout_baseline.json` keeps its figures
and the recorded graph minima. Import edge rules use only the base-against-head
graph diff. Stored edge lists are removed; `--write-baseline` refuses a head
baseline containing them and leaves the baseline untouched. A smaller SCC maximum must be recorded.
The graph-only mode executes generation and queries without running test or
build populations. On an admitted runner, update the baseline with:

```sh
python tools/ci/bazel_gate.py graph --base BASE_SHA --head HEAD_SHA --write-baseline
```

The writer refuses structural regressions, preserves baseline history and emits the updated
baseline as an artifact. A PR may only tighten the baseline. Exceptions such as
`reach://tests:test_name` or `scc:<comma-separated sorted members>` live in
`tests/fixtures/graph_impact_allowlist.json`. Each entry needs a reason, and a PR
may only remove existing entries. Run graph-only development work on BuildBuddy
with `--jobs=16`, or through PrismaBuild admission on fleet machines.

## First adoption of the public evidence views

Rob approved the narrowly recorded #2789 graph exception in
https://github.com/RobTand/prismabuild/issues/2789#issuecomment-6620473091.
The PB adapter reads `tools/ci/public_view_adoption.json`; it does not change
the shared graph core or its baseline, tolerances, budget, or allowlist.

The manifest records six imports: each of `pbrun`, `pbwait`, and `pbstatus`
imports both `public_evidence` and `operator_view`. It includes the 1,004
generated source edges, the exact newly reached consumer identities, and
per-test source identities and maximum deltas measured against main
`32f908fefc87bc83f25e5919809dbebdea4e2b18`. Each view gains at most 598
recorded existing consumers. Each of those test closures gains at most the
two recorded view sources. `sha256` is the canonical finite JSON payload's
digest with the `sha256` field omitted; the policy code independently pins it.

The complete six-import transition must appear together. Any unrecorded typed
edge, removed edge, unrecorded consumer, excess delta, or new/merged SCC
rejects the grant. Only after validation are the recorded added edges excluded
from structural attribution. All comparisons retain the real graphs and
metrics, and the gate result records the applied manifest hash. Other checks
continue to use their existing limits. Without a new recorded import the
grant is inactive. It does not permit later consumer growth or grant a runtime
publication. A changed graph population needs a newly reviewed design and
manifest rather than an automatic refresh.

The mechanism lands before a separate first-adoption issue. Output-changing
leaves follow their explicit merge prerequisites, one labelled leaf at a time.
